## 1. 产品定义

“住得近”是一款以工作地点为起点的租房决策工具。它不替代租房平台或地图导航，而是把合法来源的房源与高德路线能力组合起来，帮助用户在租金、空间、地铁距离、通勤时间、换乘次数、步行距离和费用之间做出可解释的选择。

核心差异是从“选中一套房后查询路线”转变为“输入工作地点后批量筛选并比较房源”。MVP 只提供决策和房源来源跳转，不提供聊天、支付、签约或房东发布。

## 2. 目标用户与问题

目标用户是刚入职、换工作或对上海居住区域不熟悉的租客。用户目前需要在租房平台和地图软件之间反复复制地址，逐套查询路线并手工记录结果，难以判断“多花十分钟但少换乘一次”是否更适合长期通勤。

成功标准：用户能在一次搜索中得到最多 10 套严格符合硬条件的房源，并理解每个结果为什么被推荐。

## 3. MVP 用户流程

1. 用户输入个人邀请码，验证成功后获得 7 天搜索会话。
2. 输入一个上海工作地点，并选择最长通勤时间或目标到达时间。
3. 设置预算、整租/合租、户型、最小面积、最大地铁步行距离、通勤方式和路线策略。
4. 调节“舒适优先—时间优先”滑杆。
5. 系统先执行房源硬筛选，再对最多 12 套候选房源计算精确路线，返回前 10 套。
6. 用户在地图与列表中联动浏览，查看分项得分和推荐理由。
7. 用户可以收藏、最多比较 3 套，并跳转到标明来源的房源页面。
8. 用户可以评价前三条推荐是否有帮助。

当前完成度：**演示流程 90%；真实在线流程 30%**。步骤 2–8 已能在演示模式运行；步骤 1 及真实路线、房源数据需要 Supabase 和地图 API 正式部署。

## 4. 功能需求

### 4.1 搜索和硬筛选

当前完成度：**100%（✅ 已实现）**。筛选控件和严格过滤已完成；无结果时不会自动放宽。高德配置已接通，可解析任意上海工作地点；五个快捷地点继续用于固定基线测试。

- 工作地点：必填，仅支持上海；地址解析失败时保留输入并提示重试。
- 内测输入非预置地址时，从60套模拟房源中选择直线距离最近的12套，通过高德计算真实路线；预置地址继续使用固定路线，保证基线测试可复现。
- 任意地址的冷路线请求按个人开发者QPS节流，缓存24小时；单套路线失败不阻断其他候选。
- 月租预算：必填，范围 2,000–20,000 元。
- 租赁类型：全部、整租、合租。
- 户型：不限、1 室、2 室、3 室及以上。
- 最小面积：不限、20、30、40、50 平方米。
- 最大地铁步行：不限、5、10、15、20 分钟。
- 通勤方式：公共交通、驾车、骑行、步行。
- 公共交通策略：最快、少换乘、少步行、地铁优先、避开地铁。
- 硬条件不允许自动放宽。没有结果时展示明确空状态和修改条件入口。

### 4.2 推荐和解释

当前完成度：**95%（✅ 本地完成）**。评分公式、分项得分、路线策略和“慢 8 分钟但少换乘 1 次”解释已实现并有单元测试。剩余工作是真实路线数据校准。

- 总分 100：预算 25、面积 5、地铁距离 10、通勤 60。
- 舒适—时间滑杆 `s` 范围为 0–1。通勤子权重为：时间 `20 + 20s`、换乘 `20 - 10s`、步行 `15 - 10s`、费用 `5`。
- 所有分项先归一化到 0–1，再乘对应权重；总分四舍五入为整数。
- 每套房展示总分、分项得分以及至少一条自然语言理由。
- 当候选路线比最快路线慢不超过 10 分钟但减少换乘时，理由明确展示时间与换乘差异。

### 4.3 房源、收藏和比较

当前完成度：**85%（🟡 部分完成）**。演示房源字段、来源展示、本地收藏和三套并排对比已完成。真实房源授权、过期自动处理和来源可用性仍待接入验证。

- 房源字段：标题、区域、地址、坐标、月租、租赁类型、户型、面积、图片、地铁站、步行分钟、建成年份、亮点、描述、来源、来源链接、更新时间和状态。
- 只返回 `active` 且未过期的房源。
- 未登录收藏保存在浏览器本地。
- 对比上限为 3 套，展示租金、面积、地铁步行、通勤时间、换乘、步行和费用。
- 来源链接使用新窗口打开，并明确提示用户在来源平台核验真实性。

### 4.4 状态与错误

当前完成度：**85%（🟡 部分完成）**。加载、空结果、普通网络错误、演示标识和重试入口已完成；真实限流、配额不足和 API 超时需要上线后验证。

- 加载：显示正在筛选房源和计算路线。
- 空结果：说明硬条件未被放宽，提供返回筛选按钮。
- 演示模式：缺少后端或高德配置时使用本地数据，并始终显示“演示数据”标识。
- API 超时：保留筛选条件并允许重试。
- 配额不足：显示当日请求已用完及次日恢复说明。
- 数据新鲜度：每张房源卡展示更新时间；超过 7 天标记“请核验”。

### 4.5 邀请与运营管理

当前完成度：**95%（🟡 部分完成）**。数据库、邀请码验证、7 天会话、每分钟/每日限流、管理员账号和管理函数均已部署；邀请码支持创建、停用、重新启用和二次确认后的永久删除。尚缺真实邀请码的在线全链路和定时清理验证。

- 每个邀请码独立生成，可设置有效期、每日限额、停用状态和永久删除。永久删除不可恢复，并通过外键级联使对应登录会话立即失效；历史搜索日志保留但解除邀请码关联。
- 默认限流为每分钟 3 次、每天 10 次；会话有效期 7 天。
- 轻量管理端支持房源新增、编辑、上下架、来源维护和更新时间刷新。
- 管理端依赖 Supabase Auth 管理员身份，不在公开页面暴露管理密钥。

## 5. 数据、隐私与安全

当前完成度：**85%（🟡 部分完成）**。代码已区分浏览器公开配置和服务端 Secret，本机开发模式保留API配置入口，生产构建完全移除入口、弹窗和密码输入框。高德Web服务Key已进入Supabase Secrets；尚需配置允许域名并将Web端securityJsCode改为服务端代理。

- 前端只允许包含高德 JS Key、Supabase URL 和 publishable key；这些配置仍需限制允许域名并启用 RLS。
- 高德 Web 服务 Key、Supabase secret key、邀请码盐值等只保存在 Supabase Secrets 或 GitHub Secrets。
- GitHub Pages及其他生产构建不得渲染API配置按钮、配置弹窗或浏览器Key输入框；只有本机开发模式允许使用调试入口。
- Web端JS Key属于浏览器公开标识，必须绑定允许域名；`securityJsCode`在内测期暂以明文方式构建，正式上线前迁移到服务端代理并轮换。
- 搜索明细保存 30 天，之后只保留去标识化聚合数据或删除。
- 不抓取未授权房源，不宣称覆盖全网；房源必须记录合法来源。
- 日志不得记录完整密钥、邀请码或可识别个人身份的信息。
- 新加坡 Supabase 仅用于少量已知人员内测，不作为中国正式生产环境。
- 内测不收集姓名、手机号、身份证等直接身份信息；测试人员应知晓数据处理区域。
- 精确工作地点不得进入长期搜索日志；路线缓存与会话之间不得建立可识别个人的长期关联。
- 国内公开上线目标为阿里云上海 RDS PostgreSQL + 函数计算，用户请求与个人级日志不经过境外后端。
- 前端必须通过统一 API 基础地址访问后端，确保迁移时不重写页面与推荐逻辑。

## 6. 非功能需求和验收

当前完成度：**45%（🟡 部分完成）**。本地构建、安全扫描和核心端到端流程已通过；真实性能、路线准确性和用户认可度必须在真实 API 与房源上线后测量。

- 精确路线候选最多 12 套，结果最多 10 套，路线缓存 24 小时。
- 缓存请求 P95 小于 4 秒，冷请求 P95 小于 10 秒。
- 30 条上海路线样本用于高德结果核验；每日随机抽查 5%，最多 20 条，使用百度作对照。
- 时间差超过 15% 或 8 分钟、换乘差超过 1 次、步行差超过 500 米时标记异常。
- 至少 30 次有效反馈中，70% 以上认可前三条推荐。
- 桌面与移动端核心流程通过端到端测试；构建产物和 Git 历史不得包含私密密钥。
