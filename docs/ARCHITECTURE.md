# 技术架构与数据流

## 总体结构

- React + Vite + TypeScript：公开搜索页和轻量管理页。
- 高德 JS API 2.0：地图渲染、地址解析和交互；未配置时使用明确标识的演示地图。
- Supabase Postgres：房源、邀请码、路线缓存、反馈、搜索日志与审计记录。
- Supabase Edge Functions：邀请码验证、限流、房源筛选、路线编排和管理员操作。
- 高德 Web 服务 API：服务端精确路线；Web 服务 Key 不进入浏览器。
- 百度路线 API：定时抽样核验，不参与普通搜索请求。

## 环境策略

| 环境 | 用途 | 数据与计算位置 | 边界 |
|---|---|---|---|
| 演示环境 | GitHub Pages 公开展示 | 浏览器本地演示数据 | 不接收真实个人信息 |
| 内测环境 | 少量已知人员验证 MVP | Supabase 新加坡 | 明确告知、最小化采集、短期保留 |
| 国内生产环境 | 面向中国用户正式服务 | 阿里云上海 RDS PostgreSQL + 函数计算 | 用户请求与日志不经过境外后端 |

Supabase 是内测实现，不是不可替换的产品核心。国内生产迁移方案见 [国内生产环境迁移设计](plans/2026-08-25-china-production-migration-design.md)。

## 平台隔离要求

- 前端只依赖统一 `API_BASE_URL` 与稳定的请求、响应类型。
- 推荐评分、硬筛选、路线解释和请求校验保持为平台无关 TypeScript 模块。
- Supabase、阿里云和数据库访问代码放入独立适配层。
- 业务表优先使用标准 PostgreSQL；新增扩展前检查国内目标数据库兼容性。
- 不引入 MVP 不需要的 Realtime、Storage 和普通租客 Auth，控制迁移成本。

## 搜索数据流

浏览器先验证邀请码并获得随机会话令牌。搜索请求携带令牌和筛选条件进入 `search-listings` Edge Function。函数按预算、租赁类型、户型、面积、地铁步行和状态执行硬筛选，最多取 12 套候选；随后读取 24 小时路线缓存，缺失项才请求高德。函数计算分项得分与解释，记录去标识化搜索日志并返回前 10 套。

开发环境没有 Supabase 配置时，前端使用同一套类型、筛选与评分函数处理演示数据。该模式用于展示与自动测试，不冒充真实房源服务。

## 安全边界

公开配置使用 `VITE_` 前缀；任何使用 `VITE_` 的值都会进入前端包，因此只能放可公开 Key。服务端 Key 存入 Supabase Secrets。数据库启用 RLS，公开客户端不能直接写房源和邀请码；管理员写操作必须通过登录身份与 Edge Function 二次校验。

内测期间不收集姓名、手机号、身份证等直接身份信息，不长期保存精确工作地点。路线缓存最长 24 小时，搜索明细最长 30 天；正式公开上线前，工作地点、路线请求、会话和日志必须迁入中国境内环境。

## 部署

GitHub Actions 在 Pull Request 和 `main` 推送时运行类型检查、单元测试、构建和密钥扫描。`main` 构建成功后发布 `dist` 到 GitHub Pages。Supabase 数据库迁移与函数部署使用单独工作流，并要求仓库 Secrets 已配置。
