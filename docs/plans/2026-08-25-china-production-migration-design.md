# 国内生产环境迁移设计

状态：已确认

确认时间：2026-08-25

适用产品：住得近 MVP

## 1. 决策与边界

少量人员内测继续使用 Supabase 新加坡托管项目，以较低成本验证邀请码、房源筛选、通勤路线、推荐解释和反馈闭环。该环境不是面向中国公众的正式生产环境。内测期间只邀请已知测试人员，明确告知测试数据可能在新加坡处理；不收集姓名、手机号、身份证等身份信息，不记录完整邀请码，不长期保存精确工作地点。路线缓存最长保留 24 小时，搜索明细最长保留 30 天并按计划清理。

正式面向中国用户上线时，目标架构为阿里云华东 2（上海）：RDS PostgreSQL 保存业务数据，函数计算 FC 承载 HTTP API，高德 Web 服务负责地址和路线计算。前端通过自有 API 基础地址访问后端，不依赖 Supabase 专有 URL。公开上线前另行完成域名、备案、隐私政策、个人信息处理告知和必要的合规评估。

## 2. 可迁移架构

前端统一调用 `API_BASE_URL` 下的稳定接口，包括邀请码验证、房源搜索、反馈和管理员房源管理。Supabase 阶段由适配器把这些接口映射到 Edge Functions；国内阶段由同名 Node.js/TypeScript HTTP 路由部署到函数计算。评分、硬筛选、路线解释和请求校验保持为无平台依赖的 TypeScript 模块；数据库查询、身份验证、日志和 Secret 读取放在平台适配层。

业务表坚持使用标准 PostgreSQL 类型和 SQL migration。允许使用 `pgcrypto`，但新增扩展前必须确认阿里云 RDS PostgreSQL 支持。首版不依赖 Supabase Realtime、Storage 或普通租客 Auth，降低迁移范围。管理员身份当前可用 Supabase Auth，迁移时改为国内身份服务或后端签发的短期会话；管理员数量少，因此不迁移密码，只重新创建管理员账户。

## 3. 数据迁移流程

迁移前冻结管理端写入并记录数据截止时间。先导出角色、结构和数据，随后在上海 RDS 创建空库、执行 migration、导入房源、邀请码、反馈和必要的路线数据。会话令牌、过期缓存和超过保留期的日志不迁移。导入后核对各表行数、主键唯一性、活动房源数量和抽样内容，再对新旧环境执行同一组搜索样本，比较前十结果、评分和推荐理由。

切换时先部署国内 API，通过测试域名完成端到端测试，再把生产 `API_BASE_URL` 指向国内域名。旧 Supabase 保持只读 7 天作为回滚窗口；确认无数据遗漏后删除个人级日志与缓存，最后再决定暂停或销毁内测项目。任何数据库密码、连接串、服务端地图 Key 只保存在云端 Secret 管理和本机未跟踪环境文件中。

## 4. 错误处理与验收

国内 API 保持现有错误类型，前端继续识别邀请码无效、限流、无结果、路线超时和服务不可用。数据库写操作必须具备事务或幂等键，避免重试产生重复反馈和日志。切换前要求单元测试、桌面和移动端端到端测试、密钥扫描全部通过；至少使用 30 条上海路线样本验证新旧环境结果，核心表行数必须一致，活动房源数量必须一致，随机抽查数据不得出现乱码或坐标偏移。

迁移成功的定义是：真实用户请求不再经过新加坡 Supabase；工作地点、路线请求、会话和日志均在中国境内处理；前端功能和推荐排序无明显回归；旧环境具备可验证的清理记录。
